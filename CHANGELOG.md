## v1.0.0dev - [date]

Initial release of nf-core/hlarnaseq, created with the [nf-core](https://nf-co.re/) template.

### `Added`

- Added required `--rna_samples` and `--hla_region` inputs and extraction of arcasHLA-ready paired MHC FASTQs with samtools.
- Added per-sample validatefastq pairing validation for extracted arcasHLA reads, with validation logs under `arcashla/validation/`.
- Added an `ARCASHLA_GENOTYPE` step that runs `arcasHLA genotype` on validated RNA reads (configurable via `--arcashla_genes`), writing per-sample results under `arcashla/genotype/`. Genotyping runs inside a dedicated, operator-prepared `arcas-hla` Conda environment.
- Added an `ARCASHLA_COMBINE` step that merges per-sample arcasHLA genotype JSON results into a single long-format `arcashla/arcasHLA_combined.csv`, using a new `bin/combine_arcashla_genotypes.R` script.
- Added a standalone `bin/call_hla_consensus.py` script (argparse CLI) that calls a consensus HLA allele per WGS individual by combining `ARCASHLA_COMBINE` RNA genotypes with `HLALA_COMBINE` WGS genotypes via an RNA/WGS sample key. Not yet wired into the Nextflow workflow.
- Added a `--sample_key` pipeline parameter (comma-separated `rnaseq_sample_id,wgs_sample_id` mapping) and a new `HLA_CONSENSUS` process that wires `bin/call_hla_consensus.py` into the Nextflow workflow, running automatically when `--rna_samples`, `--wgs_samples`, and `--sample_key` are all provided, with results written to `hla_consensus/`.
- Added optional `--rna_excluded_samples`/`--wgs_excluded_samples` parameters (plain-text sample ID lists) and `--hla_consensus_truncate_fields` (default `2`), passed through to `HLA_CONSENSUS`.
- Added a `bin/consensus_to_hlapm.py` script that converts `hla_consensus.rna_wgs_hla_consensus.tsv` into one per-individual, 2-column HLApm input TSV per WGS group, filtered by a new `--hlapm_allowed_loci` allow-list (default `A,B,C,DRB1,DQA1,DQB1,DPA1,DPB1,DOA,DOB,G,E,F`), and a `bin/hlapm_build_personalized_ref.R` script (ported from `artifacts/scripts/hlapm-personref.R`) that runs [HLApm](https://github.com/davenportlab/HLApm)'s `bulkRNA_build_personalized_HLA_ref()` on those per-individual TSVs.
- Added `HLAPM_PREPARE_INPUT` and `HLAPM_BUILD_REF` processes and a new `HLAPM` subworkflow that wire the above scripts into the Nextflow workflow, running automatically whenever `HLA_CONSENSUS` runs (i.e. whenever `--rna_samples`, `--wgs_samples`, and `--sample_key` are all provided). `HLAPM_BUILD_REF` invokes HLApm inside a dedicated, operator-prepared `hlapm` Conda environment via `conda run -n hlapm`. Results are written to `hlapm/input/<WGS_sample_ID>.tsv` and `hlapm/personalized_ref/out/<individual_ID>/<allele>.{fa,gtf}`.
- Added a new, now-mandatory (once `--rna_samples`, `--wgs_samples`, and `--sample_key` are all provided) `--hlapm_repo` pipeline parameter pointing to a local, pre-cloned HLApm checkout, enforced via a new `hlapmRepoExistsError()` hard-error check mirroring the existing `hlalaGraphDirExistsError()` precedent.
- Vendored the [nf-core/modules `STAR_GENOMEGENERATE`](https://github.com/nf-core/modules/tree/master/modules/nf-core/star/genomegenerate) module (pinned to STAR 2.7.11b, matching the version used by nf-core/rnaseq to build this pipeline's test data) and added a new `HLAPM_LIST_STAR_TARGETS` local module and `HLAPM_STAR_INDEX` subworkflow, wired in immediately after `HLAPM`. It discovers every allele FASTA/GTF pair actually present under `hlapm/personalized_ref/out/<individual_ID>/*.fa` (not from any input/consensus TSV), deduplicates them by a content hash (sha256 of FASTA+GTF, not by allele name, since HLApm does not explicitly guarantee identical output for the same named allele call across individuals), and builds one shared STAR genome index per distinct allele under `hlapm/star_index/<allele_key>/star/`. `hlapm/star_index_targets/unique_alleles.csv` and `sample_alleles.csv` record the dedup mapping. Unlike the rest of the pipeline, this step expects STAR from a container (`-profile singularity`/`docker`) or an auto-managed Conda environment, not an operator-prepared one.
- Vendored the [nf-core/modules `STAR_ALIGN`](https://github.com/nf-core/modules/tree/master/modules/nf-core/star/align) module (pinned to the same STAR 2.7.11b version used for indexing) and added a new `HLAPM_RESOLVE_SAMPLE_ALLELES` local module plus `HLAPM_STAR_ALIGN` subworkflow, wired in immediately after `HLAPM_STAR_INDEX`. For every RNA sample with one or more personalized HLA allele references, this aligns that sample's arcasHLA MHC-extracted reads against every one of its allele-specific STAR indexes (one `STAR_ALIGN` job per `(RNA sample, allele)` pair, reusing the same reads across each of that sample's alleles). `HLAPM_RESOLVE_SAMPLE_ALLELES` bridges `sample_alleles.csv`'s WGS-individual-ID/`RNA_ONLY:<rna_id>` keying back to real RNA sample ids using `--sample_key` (broadcasting a WGS individual's full allele set to every RNA sample matched to it), publishing the resolved mapping as `hlapm/star_align/rna_sample_alleles.csv`. Alignment output (`STAR --outSAMtype BAM SortedByCoordinate`) is written under `hlapm/star_align/<rna_id>/<allele_key>/`. Continues the same STAR container/Conda exception as `STAR_GENOMEGENERATE`.
- Vendored the [nf-core/modules `SAMTOOLS_SORT`](https://github.com/nf-core/modules/tree/master/modules/nf-core/samtools/sort) module and added two new local modules (`HLAPM_COMBINE_GTF`, `HLAPM_QUANTIFY_READS`) plus a new `HLAPM_STAR_QUANTIFY` subworkflow, wired in immediately after `HLAPM_STAR_ALIGN`. For every `(RNA sample, allele)` pair, `SAMTOOLS_SORT` additionally queryname-sorts `STAR_ALIGN`'s coordinate-sorted BAM (`samtools sort -n`, published as `hlapm/star_align/<rna_id>/<allele_key>/<rna_id>.<allele_key>.queryname.bam`, alongside the unaffected coordinate-sorted BAM). `HLAPM_COMBINE_GTF` concatenates every distinct allele's GTF into one cohort-wide `hlapm/quantify/combined.gtf` (comment lines stripped), built once per pipeline run. `HLAPM_QUANTIFY_READS` then runs the legacy, unmodified Python 2.7 `make_a_table_210804_allHLAgenes.py` script (added to `bin/`) once per RNA sample, over that sample's full set of queryname-sorted per-allele BAMs plus `combined.gtf`, producing `hlapm/quantify/<rna_id>/<rna_id>.edit_distance.tsv` (per-read edit-distance/gene-assignment table) and `.stat.txt` (run statistics), run inside a new, dedicated, operator-prepared `hlapm-quantify` Conda environment (Python 2 + `pybam` + `intervaltree`; R packages for gene-level summarization are deliberately not added yet). **This is a partial quantification step**: it stops at the per-read edit-distance table and does not yet produce a gene-level read-count summary (`<rna_id>.HLA_gene_summary.tsv`) - that requires an additional R summarization step, deferred to a later iteration.
- Installed the [nf-core/modules `HLALA_TYPING`](https://github.com/nf-core/modules/tree/master/modules/nf-core/hlala/typing) module (hla-la 1.0.4, with its own `environment.yml`/`conda` directive and matching pinned Biocontainers/Galaxy-depot `container`) and rewired the `HLALA` subworkflow onto it. The module is installed unmodified. Its companion `hlala/preparegraph` module is deliberately **not** installed: the prepared HLA-LA graph stays an operator-prepared external input (`--hlala_graph_dir`/`--hlala_graph`, unchanged in name, default, and meaning), which the pipeline never builds.
- Added a new `bin/summarize_hla_readcounts.R` script (adapted from `davenportlab/HLApm_farm_pipeline`'s `04_04_24_summarize_readcounts_script.R`) and a new `HLAPM_SUMMARIZE_READCOUNTS` local module, wired into `HLAPM_STAR_QUANTIFY` immediately after `HLAPM_QUANTIFY_READS`. For every RNA sample, it turns that sample's `<rna_id>.edit_distance.tsv` per-read table into a per-gene read count, keeping only non-`ambiguous` reads with a winning-gene edit distance at or below a new `--hlapm_quantify_max_edit_distance` parameter (default `16`), and writing `hlapm/quantify/<rna_id>/<rna_id>.HLA_gene_summary.tsv` (columns `gene_name`, `n_reads_mapping`). This closes the "stops at the per-read table" gap left open by the previous bullet. Runs inside the same `hlapm-quantify` Conda environment, which now also needs R (>= 4.0) plus the `dplyr`/`tidyr` CRAN packages.
- Added `scripts/build_reference_hlala.sh <output-dir>`, an operator tool (no pipeline behaviour change) that prepares the `--hlala_graph_dir`/`--hlala_graph` input in one command: it downloads the published `PRG_MHC_GRCh38_withIMGT` PRG graph package (~2.25 GB, resumable via `curl -C -`, following the `www.well.ox.ac.uk` &rarr; `www.chg.ox.ac.uk` redirect), verifies its md5 (`525a8aa0c7f357bf29fe2c75ef1d477d`, documented in HLA-LA's README), extracts it, and indexes it with `/usr/local/opt/hla-la/bin/HLA-LA --action prepareGraph --PRG_graph_dir <graph>` inside the same pinned `hla-la:1.0.4` container image `HLALA_TYPING` itself runs (writable bind mount, since `prepareGraph` writes `serializedGRAPH` into the graph directory) - mirroring the deliberately-not-installed nf-core `hlala/preparegraph` module. Unlike `ARCASHLA_GENOTYPE`'s reference, no companion image-build script is needed: the Biocontainers/Galaxy-depot image is public. The script checks free space (~35 GB needed for the ~29 GB indexed graph plus tarball) and warns below 40 GB of RAM _before_ downloading, and is idempotent - an already-indexed graph short-circuits ahead of the download, and an interrupted run resumes at indexing. Rebuilding means deleting the graph directory; there is deliberately no force-rebuild flag. `GRAPH_NAME`/`GRAPH_URL`/`GRAPH_MD5`/`TARBALL`/`IMAGE_TAG`/`SIF_PATH`/`REQUIRED_GB` overrides support the other _published_ graph packages, offline copies, and host moves. The script (and `docs/usage.md`) state explicitly that it fetches and indexes published graphs only: constructing a PRG graph from scratch is not scriptable outside the tool author's environment (HLA-LA's `src/Update graphs.txt` documents Perl scripts on a Windows laptop, the separate older MHC-PRG v1 binary, hardcoded cluster paths, and undistributed inputs), so it is an upstream request rather than a missing feature here.
- Added an alternative genotype-side HLA caller: **HIBAG** HLA imputation from SNP-array data, as an alternative to HLA-LA from WGS. A new `--array_samples` samplesheet (`array_sample_id,array_bed_path,array_bim_path,array_fam_path`, validated by `assets/schema_array_samples.json`) supplies PLINK BED/BIM/FAM datasets; a new `bin/hibag_predict.R` script plus `HIBAG_PREDICT`/`HIBAG_COMBINE` local modules and a `HIBAG` subworkflow run `HIBAG::hlaPredict()` over every locus in a pre-fit model and write `hibag/HIBAG_combined.tsv` in **exactly** the `sample_id`/`Locus`/`HLA_allele` contract `HLALA_COMBINE` produces, so `HLA_CONSENSUS` consumes either caller's output unchanged (HLA-LA's G-groups and HIBAG's two-field alleles both collapse to the same resolution under `--hla_consensus_truncate_fields`). `--array_samples` and `--wgs_samples` are **mutually exclusive** and rejected together by a new `genotypeSourceExclusiveError()` check. New parameters: `--hibag_model` (required with `--array_samples`, checked by `hibagModelExistsError()`), `--hibag_match_type` (default `RefSNP+Position`), `--hibag_assembly` (default `hg19`), `--hibag_loci` (default: every locus in the model), and `--hibag_min_prob` (default `0`, matching HLA-LA's lack of a confidence filter). Note that a samplesheet row is one PLINK **dataset**, not one sample: HIBAG predicts every sample in a fileset at once, and the sample IDs used downstream come from the `.fam` IID column rather than from `array_sample_id`. `bin/hibag_predict.R` pre-checks model/genotype SNP overlap and, instead of HLA-LA-style abort, reports how many model SNPs each match criterion would find and which one to switch to - the common failure being a model whose coordinates are offset from the array manifest. `HIBAG_PREDICT` provisions HIBAG itself, via a module-owned `environment.yml`/`conda` directive and a matching pinned `container` directive (see `Changed` below). Added a `test_hibag` profile (`conf/test_hibag.config`), pipeline tests in `tests/hibag.nf.test`, module tests for `HIBAG_PREDICT`/`HIBAG_COMBINE`, and `HLA_CONSENSUS` tests asserting that HLA-LA and HIBAG inputs yield identical consensus output. Test fixtures under `tests/fixtures/hibag/` include HIBAG's bundled HLA-A example model (vendored, GPL-3, provenance recorded in that directory's `README.md`) and NA12878's own OmniExpress genotypes subset to that model's SNPs, making the module test a real imputation with a known right answer (`A*01:01`/`A*11:01`).
- Added `testdata-make/10-prepare-na12878-array-hibag` and `testdata-make/lib/finalreport_to_plink.py`, which download the NA12878 / GM12878 Illumina HumanOmniExpress-24 v1.0 SNP-array data from GEO (GSE96790, `GSM2544145`) and convert it into the PLINK BED/BIM/FAM genotypes HIBAG consumes. The GEO Nexus FinalReport carries no genotype calls (no `GType`/`Allele*` columns), so genotypes are derived from the B Allele Freq clusters and the `[A/B]` allele pair, with a GC Score cutoff; the conversion log records this explicitly along with per-sample call/missingness tallies and the strand-ambiguous SNP count. Output is subset to the xMHC by default (`ARRAY_REGION`, a deliberate superset of HIBAG's own import window) to keep the artifact small. The IDATs are downloaded for provenance only - genotyping them would need a licensed BPM/EGT manifest and Illumina's `iaap-cli`.
- Added `testdata-make/11-download-hibag-model`, which downloads a published HIBAG pre-fit model covering all seven classical loci (A, B, C, DRB1, DQA1, DQB1, DPB1) from the "HLARES" parameter estimates of Zheng et al. (2014), validates it structurally, and prints its locus/SNP/allele table. `HIBAG_ANCESTRY` (European/Asian/Hispanic/African) and `HIBAG_MODEL_ASSEMBLY` (hg19/hg18) select which; European/hg19 is the default, matching NA12878's CEU ancestry. The model bundled with the HIBAG R package - this repo's test fixture - covers HLA-A only, so a run using it reported one locus. Upstream publishes no checksum and no licence for these files, so the recorded md5 is a change-detector rather than an authenticity check (a mismatch warns, it does not fail), and the model is downloaded into gitignored test data rather than vendored. `pipeline_testdata_run.sh` now defaults to this model and hard-fails with instructions if it is absent, rather than silently falling back to the single-locus fixture.
- Added a `--hibag_min_matched_snps` parameter (default `0.5`) guarding against silently wrong HIBAG calls. HIBAG does **not** fail when only part of a model's SNPs are found - it returns confident-looking alleles computed from whatever matched. Observed against the published model, whose 2012-era rsIDs have largely been merged or retired: under the pipeline's default `--hibag_match_type RefSNP+Position` only 13 of 273 HLA-A SNPs matched and the run produced a spurious homozygous `C*07:01`/`C*07:01`, where `Pos+Allele` matched 271 of 273 and gave the correct `C*01:02`/`C*07:01`. `bin/hibag_predict.R` now fails below the threshold with the same diagnostic table as the zero-overlap error, naming the criterion that would work, and logs the matched fraction per locus. Set to `0` to disable.
- Vendored the [nf-core/modules `SUBREAD_FEATURECOUNTS`](https://github.com/nf-core/modules/tree/master/modules/nf-core/subread/featurecounts) module (pinned to Subread 2.1.1) and added a new `COUNTS_COMMONREF` subworkflow, wired in whenever `--rna_samples` is provided, independent of `--sample_key`/HLApm. For every RNA sample, this runs featureCounts (`--countReadPairs -g gene_id`) directly against that sample's original, full whole-genome, coordinate-sorted BAM (`--rna_samples`'s `bam`/`bai` columns) and a new, now-mandatory `--gtf` whole-genome reference GTF parameter, producing `counts_commonref/<rna_id>/<rna_id>.featureCounts.tsv[.summary]`. This is iteration 1 of 2 toward the "hijack original count matrix" roadmap item: it stops at producing the whole-genome per-sample gene-count table; reconciling it against `HLAPM_STAR_QUANTIFY`'s HLA-specific counts is deferred to a later iteration. `--gtf` is enforced via a new `gtfExistsError()` hard-error check mirroring the existing `hlapmRepoExistsError()` precedent. Added a new `--rnaseq_strandedness` parameter (default `reverse`; allowed values `unstranded`/`forward`/`reverse`), merged pipeline-wide (not per-sample) into each RNA sample's metadata before the featureCounts call. Like `STAR_GENOMEGENERATE`/`STAR_ALIGN`, Subread/featureCounts is not expected from an operator-prepared Conda environment; the pipeline relies on the module's own published container/`environment.yml` under `-profile singularity`/`docker`/`conda`.
- Added a new `bam` output to `ARCASHLA_EXTRACT` (`modules/local/arcashla/extract/main.nf`), exposing its existing, previously-undeclared `<rna_id>.mhc.namesort.bam` intermediate (the HLA-region-restricted, primary-alignment-only, name-sorted BAM slice that its own FASTQ outputs are derived from), and a new `hla_region_bam` emit on the `ARCASHLA` subworkflow forwarding it up to `workflows/hlarnaseq.nf`. Published as a side effect under `arcashla/extracted/<rna_id>.mhc.namesort.bam`.
- Added a new `COUNTS_COMMONREF_HLA` subworkflow (iteration 2 of 2 toward "hijack original count matrix"), wired in immediately after `ARCASHLA` whenever `--rna_samples` is provided, independent of `--sample_key`/HLApm. For every RNA sample, this runs `SUBREAD_FEATURECOUNTS` a second time (aliased `SUBREAD_FEATURECOUNTS_HLA` - this repository's first use of Nextflow's `include { X as Y }` module-aliasing syntax) with `-R BAM --countReadPairs -g gene_id` against `ARCASHLA_EXTRACT`'s HLA-region BAM (above) and the same cohort-wide `--gtf` reference `COUNTS_COMMONREF` already uses (no separate HLA-only GTF). A new local `COUNTS_COMMONREF_HLA_REFORMAT` process (`modules/local/counts_commonref_hla/main.nf`) then converts the `-R BAM` reannotated BAM to plain text with `samtools view`, filters to `Assigned`-status lines, and reformats the result into a `read_name`, `direction`, `gene_name`, `edit_distance` per-read TSV using a new, verbatim-ported `bin/reformat_rnaseq_featurecounts.py` script, producing `counts_commonref_hla/<rna_id>/<rna_id>.rnaseq_featurecounts.tsv` (+ `.featureCounts.tsv.summary`). This is an intermediate artifact for a future reconciliation ("hijack") step, not a final HLA gene-count table; reconciling it against `HLAPM_STAR_QUANTIFY`'s `edit_distance.tsv` remains out of scope for this iteration.
- Patched `modules/nf-core/subread/featurecounts/main.nf` via `nf-core modules patch subread/featurecounts` (this repository's first use of `nf-core modules patch`) to add a new, `optional: true` `tuple val(meta), path("*.featureCounts.bam"), emit: bam` output, capturing `-R BAM`'s previously-uncaptured per-read reannotated BAM (needed by `COUNTS_COMMONREF_HLA` above; the plain, non-`-R BAM` `COUNTS_COMMONREF` call is unaffected since the output is optional).
- Added a new `bin/reconcile_hla_readcounts.py` script (an adaptation of `artifacts/scripts/compare-hla-rnaseq-readcounts.py`'s read-pair reconciliation logic), a new `HLA_READCOUNT_RECONCILE_DIFF` local module, and a new `HLA_READCOUNT_RECONCILE` subworkflow (iteration 3 of the "hijack original count matrix" roadmap item), wired in immediately after `HLAPM_STAR_QUANTIFY` inside the existing `--rna_samples && --sample_key` block. For every RNA sample that has both a `counts_commonref_hla` read-gene-assignment table (from `COUNTS_COMMONREF_HLA`, above) and a personalized-HLA `edit_distance.tsv` (from `HLAPM_STAR_QUANTIFY`, above) - joined by a plain `.join()` on `rna_id`, an inner join that silently skips samples with no personalized-HLA quantification - this classifies every personalized-HLA read pair as kept (`missing_fc`/`both_hla`/`reassigned_to_hla`) or dropped (`dropped_due_to_better_non_hla`, a better non-HLA `counts_commonref_hla` assignment), then emits `hla_readcount_reconcile/<rna_id>/<rna_id>.hla_readcount_reconcile.tsv` with columns `gene_id`, `gene_name`, `category` (`hla`/`non_hla`), `original_fc_count`, `personalized_count`, `diff`. Unlike the prototype script (whose `value_counts()`-only approach silently dropped an HLA gene whose every read pair was reassigned away), every post-filter personalized-HLA gene is guaranteed a row, reindexed to `0` where needed; a non-HLA gene only gets a row when it lost at least one read pair to HLA. Every gene name in the output (HLA and non-HLA alike, unlike `artifacts/scripts/hijack-original-featurecounts.py`'s own `HLA-`-only gene-mapping helper) is resolved to a `gene_id` via the whole-genome `--gtf`: a name absent from `--gtf` soft-fails to the literal string `NA` (warned, not fatal), while a name ambiguously mapping to more than one distinct `gene_id` hard-fails the run (an intentional asymmetry, since this table feeds a future patching step that must not silently guess a wrong `gene_id`). Reuses the existing `--hlapm_quantify_max_edit_distance` parameter (default `16`) as this step's edit-distance threshold too. This iteration produces only the per-sample diff table; merging/patching `counts_commonref`'s whole-genome table using it remains a future iteration.
- Added a new `bin/check_gtf_hla_gene_ids.py` script (Python standard library only) and a new `GTF_HLA_GENE_ID_CHECK` local module that **reject a `--gtf` whose HLA-region annotation does not carry a one-to-one `gene_name` <-> `gene_id` mapping**, before any counting or reconciliation output is produced. Called at plain workflow scope in `workflows/hlarnaseq.nf` immediately after `ch_gtf` is built and before `COUNTS_COMMONREF`, so it is submitted in the first scheduling wave and runs on every launchable run (`--rna_samples` and `--gtf` are both required parameters, so there is no configuration that skips it). Scope is the **union** of (a) gene rows overlapping `--hla_region` - the same samtools region string `ARCASHLA_EXTRACT` slices with, and therefore exactly the non-HLA gene names the reconciliation can see - and (b) gene names starting with `HLA-` anywhere in the file, which is where the personalized-reference names come from. Only `feature_type == "gene"` rows are considered (the same restriction `bin/reconcile_hla_readcounts.py`'s `load_gene_name_to_ids()` uses), so a gene with many `transcript`/`exon` rows is never mistaken for a duplicate, and distinct `gene_id`s are counted across the **whole** GTF rather than only inside the region, matching what that consumer actually does. Both directions fail: a `gene_name` with more than one distinct `gene_id` (`status=duplicated_gene_name`) and a `gene_id` carrying more than one distinct in-scope `gene_name` (`status=duplicated_gene_id`). On any offender the process exits `1` after printing **every** offending pair to stderr (uncapped - a failed task publishes nothing, so that message is the user's only copy of the list), and `conf/modules.config` gives it `errorStrategy = 'terminate'` so the run aborts at once instead of `conf/base.config`'s default `'finish'` letting an hours-long `ARCASHLA_GENOTYPE`/STAR task complete first. A successful run publishes a run-level provenance table, `gtf_hla_gene_id_check/hla_region_gene_id_map.tsv` (columns `gene_name`, `gene_ids`, `n_gene_ids`, `in_region`, `hla_prefixed`, `status`), also exposed as a new `gtf_hla_gene_id_report` workflow emit. `HLA_READCOUNT_RECONCILE`'s GTF input is gated on that report (a new `ch_gtf_checked` value channel: the same file, same shape, one added dependency edge), making it structurally impossible to produce a diff table from an unchecked GTF; `COUNTS_COMMONREF`/`COUNTS_COMMONREF_HLA` keep the plain `ch_gtf`, since both run featureCounts with `-g gene_id` and cannot be affected by name ambiguity. A GTF with no gene overlapping `--hla_region` is a non-fatal warning (`-profile test`'s `placeholder.gtf` legitimately has none, and on a real GTF this usually means a `chr6`-vs-`6` contig-notation mismatch); an unparseable `--hla_region` exits `2`. No new parameter, no opt-out and no lenient mode: `nextflow.config`, `nextflow_schema.json` and the nf-schema surface are untouched. The module shares `containers/datatools/environment.yml`/`quay.io/hlarnaseq/datatools:1.1` (stdlib-only script, so no package, image or tag change), reports `python3` in `versions.yml`, keeps the datatools "no profile" guard so a missing environment stays exit `127` rather than being confused with a uniqueness failure, and deliberately has **no `stub:` block**, so `-stub-run` exercises the real check.
- Added `scripts/patch_gtf_gene_ids.py`, an operator tool (no pipeline behaviour change, Python standard library only) that mechanizes the two fixes `docs/usage.md` "Fixing a rejected GTF" describes for a `--gtf` that `GTF_HLA_GENE_ID_CHECK` rejects, so a corrected GTF is reproducible from a small reviewable patch file rather than an ad hoc `awk` invocation nobody kept. It takes a two-column TSV of `gene_id` and an optional `new_gene_name`, reads the GTF plain or gzipped, and prints the patched GTF to stdout with a per-gene action summary on stderr. A listed `gene_id` with a `new_gene_name` is **renamed**; a listed `gene_id` without one is **removed**. Both actions are keyed on the row's own `gene_id` attribute and therefore reach the whole gene - every `transcript`/`exon`/`CDS`/`UTR`/codon row carries the same `gene_id` - which is what makes the fix effective downstream, since featureCounts reads `exon` rows and renaming only the `gene` row would leave the old name in the counts. A rename substitutes the `gene_name "..."` token and nothing else, so attribute content, order and whitespace survive unchanged and the file is never re-serialized from a parsed attribute dict. **Nothing is inferred from `gene_name`**: a row is removed only when its own `gene_id` is listed with no replacement name, so an unlisted gene that merely shares a symbol with a listed one is untouched - which is what makes the `Y_RNA` case safe, since naming the 7 in-region `gene_id`s cannot disturb the 751 copies elsewhere in the genome. A `gene_id` listed in the patch but absent from the GTF is a hard error (exit `3`), not a silent no-op, and the patch is resolved against the GTF in a first pass before the first output byte, so a stale patch or the wrong `--gtf` leaves stdout empty rather than a truncated file that looks usable; an unusable input - a malformed patch row, a duplicate `gene_id`, a `new_gene_name` containing a quote or tab, or a file that cannot be read - is exit `2`. Since stdout is a whole GTF, SIGPIPE keeps its default disposition, so piping into `head` or into a `gzip` that dies ends quietly with `141` instead of a `BrokenPipeError` traceback. Renaming onto a name another gene already owns, or renaming two `gene_id`s to the same name, warns on stderr rather than failing - `bin/check_gtf_hla_gene_ids.py` remains the authority on whether the result is acceptable. Also added `gencodev50.mapping_patch.tsv`, the complete rename-only patch that makes stock `gencode.v50.primary_assembly.annotation.gtf.gz` pass the check under the default `--hla_region` (12 `gene_id`s: the `HLA-DRB6`/`HLA-H`/`HLA-L`/`HLA-V` pseudogene twins, the `POLR1HASP` lncRNA twin, and the 7 in-MHC `Y_RNA` copies renamed per locus), with its provenance and the reasoning behind each primary-id choice in its comment preamble; applying it rewrites 473 of the GTF's 11,254,876 feature rows and removes none. Documented in a new `docs/usage.md` "Patching a rejected GTF" section. The script is not run by any process, so it adds no `environment.yml`, `conda`/`container` directive, `versions.yml` entry or citation; the documented invocation nevertheless runs it inside the existing `containers/datatools` image so the operator need not rely on a host interpreter either.
- Added `scripts/sanger_hpc_deploy_scripts/`, an [Environment Modules](https://modules.readthedocs.io/) deployment of the pipeline for an LSF cluster (adapted from the [yascp](https://github.com/wtsi-hgi/yascp) v2.0 deploy scripts; no pipeline behaviour change, no new or re-defaulted parameter, and nothing under `conf/` touched). A modulefile template (`sanger_module_files/1.0`) puts four commands on `PATH`: **`hlarnaseq`** runs the pipeline in the foreground and **`hlarnaseq-bsub`** submits the Nextflow **head process** to LSF via `bsub`, both defaulting to `-profile singularity,sanger` and passing every remaining argument to `nextflow run` unchanged; **`hlarnaseq-build-image <datatools|arcashla|hlapm|hlapm-quantify|all>`** and **`hlarnaseq-build-reference <arcashla|hlala> <output-dir>`** are plain dispatchers (no `bsub` wrapper) over the existing `scripts/build_image_*.sh` and `scripts/build_{arcashla_reference,reference_hlala}.sh`, which keep all the build logic. Both profiles are needed and in that order: `singularity` (this repo's own) enables the container engine, while `sanger` comes from [nf-core/configs](https://github.com/nf-core/configs) - consumed upstream rather than vendored here - and supplies the LSF executor, farm22 queue selection by `task.time`/`task.memory`, and the `--bind /lustre --bind /nfs --bind /data --bind /software` mounts, but does **not** enable Singularity itself. There are deliberately **no site defaults** for `--gtf`/`--arcashla_reference_dir`/`--hibag_model`/`--hlala_graph_dir`: users supply their own exactly as on a bare `nextflow run`. Deployment is parametrised rather than hardcoded - the wrappers resolve the pipeline from their own (symlink-resolved) path, so a git checkout, a versioned `/software/...` install and a scratch copy all work unedited, and the only deploy-edited files are the modulefile's install path plus an optional, gitignored `site.env` (container cache, default queue, head-job memory) whose values a user's own environment always overrides. `lib/common.sh` holds all shared logic - pipeline location, `NXF_*`/`SINGULARITY_TMPDIR` exports, and command assembly - rather than yascp's ten near-identical copies, and `-profile` is injected only when the caller passed none, so `hlarnaseq -profile conda ...` never yields two `-profile` options. `DRY_RUN=1` prints the assembled `nextflow run`/`bsub` command and exits. Deliberate departures from the yascp originals, each documented in that directory's `README.md`: Nextflow runs in the **foreground** of the LSF job (yascp backgrounds it with `&` inside the job script, so the script exits at once and the head process is orphaned, leaving `bjobs`/`bkill` describing nothing); there is no separate job script at all (yascp pairs every `bsub_*.sh` with a `nohup_start_nextflow_lsf*.sh`), `hlarnaseq-bsub` instead submitting `hlarnaseq` itself as one already-quoted command string, since `bsub` re-joins its trailing words and the job re-parses them through a shell, so passing argv as separate words would lose the quoting on any argument containing whitespace; logs go to a timestamped `./hlarnaseq-run-logs/<timestamp>/` instead of `rm -f *.log` in the user's working directory; no interactive container-cache prompt (it would hang under `bsub`); no `ts`/moreutils dependency and no `/dev/tcp` usage pings; no `--nf_ci_loc` (not a parameter here - nf-schema would flag it as unrecognised); no automatic `-resume`; and `$install/bin` is **not** added to the user's `PATH`, since those scripts are staged into tasks by Nextflow and run under each module's own declared interpreter. Note that `hlarnaseq-build-image` requires Docker (the underlying scripts build with `docker build` and convert via `docker-daemon://`), so on a Singularity-only cluster the four unpublished images' `.sif` files must be produced elsewhere and copied into the install tree that `${projectDir}`/`${moduleDir}` resolve against - recorded as a known limitation, since publishing those images to a registry is the real fix. Documented in a new `docs/usage.md` "Running on an LSF cluster (Sanger module)" section and in `scripts/sanger_hpc_deploy_scripts/README.md`.

The check now also requires `hla.idx` and `hla.p.json` - files only ever produced by `arcasHLA reference` itself - and names `scripts/build_arcashla_reference.sh` in the error. **This rejects at launch some directories that were previously accepted and then failed mid-run**, which is the intent. Stub runs are exempt, so `-profile test`'s deliberate `tests/fixtures/arcashla_reference_stub/` placeholder still works.
- Fixed `STAR_GENOMEGENERATE` requesting the `process_high` label's defaults (12 CPUs, 72 GB) regardless of genome size, which exceeded the CPUs/memory available on smaller machines. HLA allele references are a few KB each, so `conf/modules.config` now caps it at 1 CPU and 2 GB (`* task.attempt` on retry) for this process specifically.
- Fixed `SUBREAD_FEATURECOUNTS`'s version-reporting `eval` (`featureCounts -v 2>&1 | sed 's/featureCounts v//'`) corrupting the entire `pipeline_info/nf_core_hlarnaseq_software_versions.yml` file whenever `featureCounts` is not on `PATH` (i.e. without `-profile conda`/`singularity`/`docker`): the resulting `bash: ... command not found` stderr text was piped through unmodified (since it does not match `sed`'s substitution pattern) and written as the "version" string, and its embedded colon breaks YAML parsing of the whole file, not just this one entry. Bundled into the same `nf-core modules patch subread/featurecounts` operation as the new `bam` output above; the `sed` invocation now uses `-n '...p'` so only lines actually matching `featureCounts v...` are emitted, degrading gracefully to an empty/`null` version field (matching the pre-existing `STAR_ALIGN`/`STAR_GENOMEGENERATE` `eval` precedent) instead of corrupting the file. Confirmed via a real `-stub-run` in a `featureCounts`-less, container/conda-less environment that `pipeline_info/nf_core_hlarnaseq_software_versions.yml` now parses as valid YAML.
